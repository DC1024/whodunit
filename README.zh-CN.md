# whodunit

**查出是谁、在什么时候，把这台 Windows 改成这样的。**

Windows 记下了值，但从不记下作者。所以当你发现 26H2 忽然不出现了、休眠从电源菜单里消失了、
默认打印机自己换了，你手上只有一个"结果"，无从追问是谁干的。

`whodunit` 就是干这个的：一条命令、一个现象、一条归因链。查不出凶手的时候，它明说"查不出"，
而不是编一个给你。

---

## 它不是什么

先把边界说清楚，省大家时间：

- **不是体检工具**。不给你打分，不列"发现 37 项问题"。那类工具已经过剩了。
- **不是优化工具**。它只读不写。还原命令打印出来，跑不跑你自己决定。
- **不是 ProcMon**。ProcMon 必须在改动**发生之前**就开着——你之所以在这儿，正是因为它没开。
- **不是取证套件**。RegRipper 那类是给取证人员对着磁盘镜像用的，这是给坐在机器前的人用的。

## 为什么现有工具都不行

| 工具 | 能做什么 | 为什么解决不了这个问题 |
|---|---|---|
| Process Monitor / RegFromApp | 实时抓注册表写入 | 必须提前运行，事后完全没用 |
| Regshot / SysTracer | 快照对比 | 只告诉你"变了什么"，不告诉你"谁变的"，还得你事先拍过快照 |
| Sysinternals Policy Analyzer | 组策略对比 | 手动、不归因、没有结论 |
| winutil / Sophia Script / privacy.sexy | 应用各种优化 | 这些恰恰是**制造**你问题的东西，不是解释它的 |
| `gpresult /h` | 导出策略结果集 | 只覆盖策略，而且读不读得懂全靠你自己 |

真正的空位是：**事后归因**，而且是在一台从没为排查做过任何准备的机器上。

## 安装

从 [releases 页面](https://github.com/DC1024/whodunit/releases) 下载对应你电脑的包，
里面有两个二进制，都是单文件静态二进制、免安装、无数据文件：

| 二进制 | 用在哪 |
|---|---|
| `whodunit.exe` | 命令行——脚本、登录任务、`-json` 输出 |
| `whodunit-gui.exe` | 双击，报告直接在浏览器里打开 |

GUI 没有用控件库：任何原生 GUI 方案都要 cgo 或一大坨依赖，而 whodunit 的立身之本是
`CGO_ENABLED=0` 的单文件。所以它是本机回环 HTTP 服务 + 编译进去的页面，只监听 `127.0.0.1`，
不对外。它显示的报告与命令行打印的是同一份（同一个函数生成），窗口里和贴到论坛里的不会打架。

**只发布 Windows 版本。** CI 确实会交叉编译 linux/amd64，但那是为了保证非 Windows 的 stub 不被写坏，
不是给你下载用的——whodunit 排查的就是 Windows 机器。

不需要管理员权限就能读。每个包里每个二进制都带了 `.sha256`，下载后建议核对。

项目主页：<https://whodunit.app.workbuddy.host/>

```powershell
whodunit why "26H2 装不上"
```

或者自己编译：

```bash
go build ./cmd/whodunit
```

## 用法

```
whodunit rules                 列出内置规则
whodunit scan                  跑全部规则，报告命中的
whodunit why "<现象>"           按现象匹配规则并归因
```

参数：`-json` 输出 JSON，`-rules <目录>` 用你自己的规则目录，`-lang <代码>` 切换报告语言（`auto` / `en` / `zh`，默认 `auto`——按系统区域自动选，中文 Windows 默认中文）。

每条规则都同时带了中文与英文文案；报告外壳（标题、字段标签 `observed` / `subject` / `attributed to`、证据表、回滚步骤、以及「未匹配到原因」这类提示）也跟着同一开关切换。所以 `-lang en` 是一份**通篇英文**的报告，`-lang zh` 是**通篇中文**的报告，中间不会夹杂另一种语言，可以直接贴到对应语言的论坛里求助。

退出码：`0` 没命中，`1` 有命中，`2` 用法或运行错误。所以它能塞进脚本和登录任务里。

## 证据等级

每条证据都带等级，等级就是承诺。

| 等级 | 含义 | 典型来源 |
|---|---|---|
| **A** | 施动者被自己的记录点名 | 从磁盘上真正读到的工具自身变更日志 |
| **B** | 强线索：工具在这台机器上，且确实会改这类设置 | 安装痕迹、指纹库 |
| **C** | 只有时间——知道什么时候，不知道谁 | 注册表键的 FILETIME |
| **D** | 只有状态——连时间都拿不到 | 没有源能回答 |

最强证据只有 C 级时，报告写的是 `unknown actor`（凶手未知）。**不会把猜测升格成事实**——
这是整个项目的立身之本。

A 级要求施动者自己的日志里，有一行**点名了当前这个设置**。日志文件存在、但提的是别的设置，
就还是 B 级——**存在不等于认罪**。

## 规则和指纹都是数据

加一条检查 = 加一个 YAML 文件，见 [CONTRIBUTING.md](CONTRIBUTING.md)。不用写 Go 代码。

内置规则：

| 规则 | 对应现象 |
|---|---|
| `wufb-feature-update-blocked` | 功能更新（26H2 这类）一直不出现 |
| `sleep-hibernate-disabled` | 休眠消失、合盖行为不对 |
| `default-printer-hijacked` | 默认打印机自己变 |

## 已知的局限

- **A 级是少数，不是常态。** 多数机器没有可查的变更日志，所以多数归因会落在 B 或 C。
  分级体系的存在就是为了让这件事诚实。
- **策略可能会回来。** 如果是 MDM 或计划任务在持续下发，删了键过 15 分钟又回来。
  动手前先看证据链里 `policy_origin` 那一条。
- **只支持 Windows。** 其他平台会明确报告"跳过"，而不是编个答案出来。
- **指纹库只认得少数几个工具**：内置认识 Winhance、ShutUp10 等 6 个（见 `internal/sources/fingerprints/tools.yaml`）。
  不在库里的优化工具，哪怕嫌疑再明显也点不出名字——加一个是改 YAML 的事，欢迎 PR。
